# LLM Inbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a 3-pane desktop application that aggregates messages from every running Claude Code agent into one place, shows what has been replied to, and lets you reply from it.

**Architecture:** The ntfy topic that the HITL MCP server already publishes to is treated as an append-only, totally-ordered event log. Transport logic is extracted from the existing Tauri client into a shared `hitl-transport` crate. A new `hitl-store` crate turns that event stream into a local SQLite projection, where a message's status is *folded* from its events rather than stored as mutable state. A headless `hitl-archivist` retains history beyond ntfy's cache window, and a new `hitl-inbox` Tauri app renders the three panes and publishes replies.

**Tech Stack:** Rust 2021 (Tauri v2, reqwest, tokio, rusqlite), TypeScript/Node ≥18 (ESM, NodeNext) for the MCP server, vanilla-JS ES modules for webview UI, Jest (server), Playwright (client UI), `cargo test` (Rust).

**Spec:** `docs/superpowers/specs/2026-08-16-llm-inbox-design.md` — approved at revision 4. Read it before starting; this plan argues from it and does not restate its rationale.

**Scope:** 3 milestones, 9 tasks. Spec §12 (LLM summarization) and §13 (mobile) are deliberately **not planned here** — see "Deferred" at the end.

---

## Global Constraints

Every task's requirements implicitly include this section.

- **No wire-protocol change.** `PROTOCOL_VERSION` stays at 2. No new message types, no new required fields on existing types. (Spec §2 non-goals, §5.3.)
- **Node ≥ 18** (`engines.node` in `hitl-mcp-server/package.json`). CI uses Node 20.
- **TypeScript is ESM / NodeNext.** Imports of local files MUST carry a `.js` extension.
- **Jest runs under** `cross-env NODE_OPTIONS=--experimental-vm-modules`.
- **Rust edition 2021.** Existing crate is `hitl-client` v2.11.3.
- **`hitl-transport` MUST NOT take a *direct* dependency on `tauri`, `rodio`, `urlencoding`, `windows`, or `windows-sys`.** Verified in Task 2: `cargo tree -p hitl-transport` shows no `tauri`, `rodio`, or `urlencoding` at all. Note that `windows-sys` and tokio's `net` feature **do** arrive transitively through `reqwest` — that is unavoidable while `reqwest` is the HTTP client, and was equally true of `hitl-client` before the split. The mobile-compilability claim rests on `reqwest` itself being cross-platform, not on `windows-sys` being absent from the tree.
- **`hitl-transport` MUST NOT call `log::set_boxed_logger`** or otherwise install a global logger. It may only call `log::info!`/`warn!`/`error!`. Installing a process-global logger is the binary's job.
- **`hitl-transport` requests narrow tokio features**: `["rt", "sync", "time", "macros"]` — never `"full"`.
- **Milestone 1 is behaviour-preserving.** No feature changes, no bug fixes, no "while I'm here" improvements. **Measured baseline (Task 1, commit `bc1cb8a`): 167 Rust tests, 214 Jest tests, 117 Playwright tests.** All must pass identically before and after. After Task 1 the Rust count is **177** (167 + 10 crypto).
- **Ordering authority is ntfy's message id/time**, never local wall-clock and never the `timestamp` field inside a payload. (Spec §4.3.)
- **Versions must stay in sync** across root `package.json`, `server/package.json`, `client/package.json`, `client/src-tauri/tauri.conf.json`, and `Cargo.toml` — `server/src/__tests__/version-sync.test.ts` enforces this and will fail the build if a new crate's version drifts.

### Deviation from the spec, stated up front

Spec §4.4 lists "the fold" as new code inside `hitl-transport`. **This plan puts the fold in `hitl-store` instead.** Reason: the fold produces persistence projections and is only needed by consumers that keep a database (`hitl-archivist`, `hitl-inbox`). `hitl-client` needs the transport but not the fold, and forcing a rusqlite dependency on it would violate the behaviour-preserving constraint of Milestone 1. Everything else follows the spec as approved.

Append to `crypto.rs`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    const KEY: &str = "00112233445566778899aabbccddeeff00112233445566778899aabbccddeeff";

    fn parse(s: &str) -> serde_json::Value {
        serde_json::from_str(s).expect("envelope is json")
    }

    #[test]
    fn round_trips_plaintext() {
        let out = encrypt("hello world", KEY).expect("encrypts");
        assert_eq!(decrypt_value(&parse(&out), KEY).expect("decrypts"), "hello world");
    }

    #[test]
    fn round_trips_empty_plaintext() {
        let out = encrypt("", KEY).expect("encrypts");
        assert_eq!(decrypt_value(&parse(&out), KEY).expect("decrypts"), "");
    }

    #[test]
    fn round_trips_multibyte_plaintext() {
        let text = "héllo 🌍 — ünïcode";
        let out = encrypt(text, KEY).expect("encrypts");
        assert_eq!(decrypt_value(&parse(&out), KEY).expect("decrypts"), text);
    }

    #[test]
    fn two_encryptions_of_the_same_text_differ() {
        // A fresh nonce per call is the whole security property. If this ever
        // passes by equality, nonce generation has been broken.
        let a = encrypt("same", KEY).expect("encrypts");
        let b = encrypt("same", KEY).expect("encrypts");
        assert_ne!(a, b, "nonce must be fresh per encryption");
    }

    #[test]
    fn rejects_a_short_key() {
        assert!(encrypt("x", "00112233").is_err());
    }

    #[test]
    fn rejects_a_non_hex_key() {
        let bad = "zz112233445566778899aabbccddeeff00112233445566778899aabbccddeeff";
        assert!(encrypt("x", bad).is_err());
    }

    #[test]
    fn rejects_the_wrong_key_on_decrypt() {
        let other = "ffeeddccbbaa99887766554433221100ffeeddccbbaa99887766554433221100";
        let out = encrypt("secret", KEY).expect("encrypts");
        assert!(decrypt_value(&parse(&out), other).is_err());
    }

    #[test]
    fn rejects_a_tampered_ciphertext() {
        let out = encrypt("secret", KEY).expect("encrypts");
        let mut v = parse(&out);
        let data = v["data"].as_str().expect("data").to_string();
        let flipped = if data.starts_with('A') { format!("B{}", &data[1..]) }
                      else { format!("A{}", &data[1..]) };
        v["data"] = serde_json::Value::String(flipped);
        assert!(decrypt_value(&v, KEY).is_err(), "AEAD tag must reject tampering");
    }

    #[test]
    fn rejects_a_malformed_base64_iv() {
        let out = encrypt("secret", KEY).expect("encrypts");
        let mut v = parse(&out);
        v["iv"] = serde_json::Value::String("!!!not base64!!!".into());
        assert!(decrypt_value(&v, KEY).is_err());
    }

    #[test]
    fn is_encrypted_recognises_only_real_envelopes() {
        let out = encrypt("x", KEY).expect("encrypts");
        assert!(is_encrypted(&parse(&out)));
        assert!(!is_encrypted(&parse(r#"{"type":"question"}"#)));
        assert!(!is_encrypted(&parse(r#"{"_encrypted":true}"#)));
        assert!(!is_encrypted(&parse("null")));
    }
}
```

Expected: PASS. **If any fails, STOP** — that is a real bug in shipping crypto code. Report it; do not weaken the assertion to match the behaviour. Adjust only for signature mismatches (e.g. if `encrypt` returns `String` not `Result`).

- [ ] **Step 4: Define the seam**

`crates/hitl-transport/src/ntfy/mod.rs`:

```rust
use crate::types::*;

/// Everything the transport needs to hand outward. Implemented by each host
/// application: the Tauri client opens windows, the inbox writes to a store,
/// a test implementation records calls.
///
/// Implementations MUST NOT block; the subscribe loop awaits these.
pub trait NtfySink: Send + Sync {
    fn on_connected(&self, connected: bool);
    fn on_message(&self);

    fn on_question(&self, msg: &QuestionMessage, was_encrypted: bool);
    fn on_answer(&self, msg: &AnswerMessage);
    fn on_notification(&self, msg: &NotificationMessage, was_encrypted: bool);
    fn on_dismiss_notification(&self, msg: &DismissNotificationMessage);

    fn on_plan_review(&self, msg: &PlanReviewMessage, was_encrypted: bool, attachment: Option<AttachmentRef>);
    fn on_plan_review_response(&self, msg: &PlanReviewResponseMessage);
    fn on_plan_review_ack(&self, msg: &PlanReviewAckMessage);
    fn on_cancel_review(&self, msg: &CancelReviewMessage);

    fn on_sender_identity(&self, action: SenderIdentityAction, sender: SenderInfo);

    /// True when a window/view for this message id is currently open.
    /// Drives sender-identity routing (emit live vs cache for later).
    fn is_view_open(&self, message_id: &str, kind: &str) -> bool;

    /// Protocol version higher than this build understands.
    fn on_unsupported_version(&self, message_id: &str, msg_type: &str, version: u32);
}

#[cfg(test)]
pub(crate) mod test_sink {
    use super::*;
    use std::sync::Mutex;

    #[derive(Debug, PartialEq, Eq)]
    pub enum Call {
        Connected(bool), Message,
        Question(String), Answer(String),
        Notification(String), DismissNotification(String),
        PlanReview(String), PlanReviewResponse(String),
        PlanReviewAck(String), CancelReview(String),
        SenderIdentity(String), UnsupportedVersion(String, u32),
    }

    #[derive(Default)]
    pub struct RecordingSink {
        pub calls: Mutex<Vec<Call>>,
        pub open_views: Mutex<Vec<String>>,
    }

    impl RecordingSink {
        pub fn calls(&self) -> Vec<String> {
            self.calls.lock().unwrap().iter().map(|c| format!("{c:?}")).collect()
        }
        fn push(&self, c: Call) { self.calls.lock().unwrap().push(c); }
    }

    impl NtfySink for RecordingSink {
        fn on_connected(&self, c: bool) { self.push(Call::Connected(c)); }
        fn on_message(&self) { self.push(Call::Message); }
        fn on_question(&self, m: &QuestionMessage, _: bool) { self.push(Call::Question(m.message_id.clone())); }
        fn on_answer(&self, m: &AnswerMessage) { self.push(Call::Answer(m.question_id.clone())); }
        fn on_notification(&self, m: &NotificationMessage, _: bool) { self.push(Call::Notification(m.message_id.clone())); }
        fn on_dismiss_notification(&self, m: &DismissNotificationMessage) { self.push(Call::DismissNotification(m.notification_id.clone())); }
```

```ts
import { randomUUID } from 'crypto';

/** One MCP server process is exactly one Claude Code session. */
const PROCESS_SESSION_UUID = randomUUID();

export function makeSessionNameResolver(opts: {
  env: NodeJS.ProcessEnv;
  mintedUuid: string;
}): SessionNameResolver {
  // The bridge id exists only while Remote Control is active and is removed
  // when it ends — so resolve once, at first call, and stay stable after.
  let resolved: string | null = null;
  return () => {
    if (resolved === null) {
      resolved = opts.env.CLAUDE_CODE_BRIDGE_SESSION_ID ?? opts.mintedUuid;
    }
    return resolved;
  };
}

export const defaultSessionNameResolver: SessionNameResolver =
  makeSessionNameResolver({ env: process.env, mintedUuid: PROCESS_SESSION_UUID });
```

Two precedence rules the matrix does not spell out, both settled by §9.2:

- **`cancel_review` gets no special case.** The first settling event in ntfy order wins, whether that is a response or a cancel. If the response is earlier, the server read it before deciding to cancel and the human genuinely answered; if the cancel is earlier, the agent was already gone and nothing consumed the response. - **`plan_review_ack{status:"lost"}` is per-response, not per-message.** It carries `responseId`, so it applies only when it names the response the fold selected as winner. An ack naming a *losing* response is ignored by the fold — that device already learns it lost from the ack it received directly. Folding it message-wide would mark every contested message `lost`, including on the device that actually won.

A human choosing the `cancelled` **verdict** is `Answered { verdict: Cancelled }` — not `Status::Cancelled`. The human acted; `Status::Cancelled` means nobody did. Do not conflate them.

### Task 9: Reply, and handle the race

**Context:** Spec §9. Your original requirement: *"any application when it replies, any of these applications can also register the message and update the status."* Because ntfy gives every subscriber the same total order, this needs no arbiter — every device computes the same winner from the same log. That property is what Task 5's `folding_is_order_independent` test protects, and this task is where it pays off.

**Files:**
- Create: `inbox/src/reply.js`
- Modify: `inbox/src/{render-question.js,render-review.js}`, `inbox/src-tauri/src/main.rs`

**Interfaces:**
- Consumes: `hitl_transport::{publish_answer, publish_dismiss_notification, submit_review_response}`, `hitl_store::fold`.

- [ ] **Step 1: Publish replies**

`answer` / `plan_review_response` / `dismiss_notification` published through `hitl-transport`, exactly as any other device does. No new code path, no new message type.

Enforce client-side that `changes_requested` and `rejected` carry non-empty `overallFeedback` or ≥1 inline comment — the server enforces this in `normalizeResponseBody()` and will otherwise reject the submission.

Persist in-progress review comments as drafts, matching `drafts.rs` behaviour.

- [ ] **Step 2: Implement the race state machine** (§9.3)

`submitting` → `answered` (yours won) or `lost` (another device's response was earlier in ntfy order). On `lost`, show the "Answered elsewhere" banner and lock the form **without discarding the draft**.

Fold `plan_review_ack{status:'lost'}` as confirmation, but **do not depend on it** — no equivalent ack exists for questions, so the fold must be sufficient on its own.

Mark orphans explicitly (spec §16.5) rather than presenting a dead request as actionable — this is the exact failure that cost a real review submission during design.

- [ ] **Step 3: Test the property that the design rests on**

Drive **two independent `Store` instances** with the same event log and assert they agree on the winner for every race case. If they can disagree, the no-arbiter design is invalid.

- [ ] **Step 4: Verify everything and commit**

```powershell
cd hitl-mcp-server; cargo test --workspace; npm test --workspace server
cd client; npx playwright test
cd ../inbox; npx playwright test
```

`git add -A && git commit -m "feat: reply from the inbox with race-safe status"`

## Deferred — not planned here

These are in the approved spec but **deliberately have no tasks yet**. Detail written now would be guesswork; re-plan each once Milestone 3 lands and the real shapes are known.

- **LLM summarization (spec §12)** — agent digest, message explainer, catch-up. The `summaries` table is already in Task 5's schema so no migration is needed later. Constraints fixed now: **off by default** (it is the first feature that sends plan bodies and question context outside your own infrastructure), on-demand rather than automatic, keyed by `(scope, scope_key, content_hash)` and invalidated when new events arrive, and **never on the critical path** — the Inbox stays fully functional with it disabled, offline, or the key absent. It is a cached artifact, never part of the fold.
- **Mobile (spec §13)** — `tauri android init` / `ios init` on `inbox/`, panes collapsing to stacked navigation at narrow widths, dropping `#![windows_subsystem = "windows"]`. A phone joins by learning `topicId` + `encryptionKey`, the two secrets every device already shares — no tunnel, no port forwarding. Known limitation to design around: a phone on cellular cannot reach the archivist on `127.0.0.1`; exposing it beyond localhost is a separate decision with its own auth requirements.

**Bugs found during design, noted not fixed** (your call — you asked for notes only): the release pipeline shipped a v2.9.6 client binary inside npm 2.11.2, and `ensureClientRunning()` (`setup.ts:102-154`) does no version check, so a stale client can squat and silently drop newer message types. Detail in `scratchpad/conversation_memories/llm-inbox-design/05-reviewplan-bug-rootcause.md`.
